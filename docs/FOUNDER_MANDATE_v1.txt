# 5. PRIMARY PRODUCT LOOP

The central experience must follow this lifecycle:

**Discover → Join → Learn → Contribute → Verify → Improve → Reward → Build Reputation → Unlock More Opportunities → Repeat**

Example:

1. A new user signs up in seconds.
2. The system recommends a beginner-friendly project.
3. The user opens a quest.
4. The quest displays an application preview and a clear objective.
5. The user identifies a problem or suggests a feature.
6. They submit a prompt, screenshot, reproduction steps or other evidence.
7. AI evaluates, classifies and routes the submission.
8. If the contribution is useful, the system creates or updates a development task.
9. A human builder or AI agent works on the improvement.
10. Tests and independent QA evaluate the implementation.
11. An approved change is merged and deployed.
12. The contributor receives a visible outcome and eligible rewards.
13. The system invites the contributor to test the next iteration.

This cycle must operate as a real, persisted workflow.

Every participant should be able to see what happened to their contribution.

- Originality.
- Reproducibility.
- Functional correctness.
- Tests and evidence.

- Accepted but not finalized.
- Finalized entitlement, if applicable.
- Claimed or paid.

## Layer D — Ecosystem Token

Design a transferable token providing meaningful ecosystem utility.

Potential uses:

- Eligible contributor rewards.
- Access to optional ecosystem benefits.
- Community governance participation.
- Sponsored ecosystem programs.

## Layer E — Real Money Bounties

Support clearly funded USDC or other supported payments for professional work.

Funds and promised payments must be tracked distinctly from XP and token rewards.

A verified token balance is not the same as earned cash.

# 11. HUMAN-IN-THE-LOOP DEVELOPMENT ENGINE

This is the core technical innovation.

Create a closed-loop development system connecting community contributions to a continuously improving application.

The canonical workflow is:

**Community Input → Structured Feedback → AI Triage → Issue Clustering → Prioritization → WorkPacket → Agent/Human Execution → QA → Verification → Release → User Revalidation → Rewards**

### Step 1 — Feedback Intake

Accept structured or unstructured feedback.

Examples:

- "The login page crashes on mobile."
- "Add a referral progress indicator."
- "The dashboard feels confusing."
- "This screen needs better contrast."
- "I created a cleaner version using AI."

Record context, project, application version, timestamps and supporting evidence.

### Step 2 — AI Classification

Classify feedback as:

- Bug
- Feature request
- UX issue
- Performance issue
- Accessibility issue
- Documentation issue
- Security concern
- Duplicate
- Not actionable

Store classification confidence and explanation.

### Step 3 — Deduplication & Clustering

Group equivalent or related reports without discarding distinct evidence.

Aggregate signal:

- Number of affected users.
- Severity.
- Reproducibility.
- Frequency.
- Affected feature.
- Business importance.
- Contributor evidence.

### Step 4 — Prioritization

Calculate a transparent priority recommendation using impact, urgency, feasibility, cost and product direction.

Distinguish:

- Fix now.
- Include in next release.
- Add to roadmap.
- Request clarification.
- Reject with explanation.

### Step 5 — Agent OS Dispatch

Convert accepted issues into structured execution WorkPackets.

Each WorkPacket should include:

- Tenant and project IDs.
- Source feedback IDs.
- Objective.
- Scope.
- Repository and permitted paths.
- Acceptance criteria.
- Execution budget.
- Authorized tools.
- Assigned agent or human.
- Required tests.
- Risk class.
- Verification requirements.
- Expected artifact.

### Step 6 — AI / Human Execution

For authorized projects, AI agents can:

- Inspect the relevant code.
- Propose an implementation.
- Create isolated changes.
- Run tests.
- Open pull requests.
- Produce previews.
- Respond to review feedback.

Humans can take over, collaborate or review.

### Step 7 — Independent Verification

Require proof of completed work.

A completion claim is valid only when its evidence supports it.

Distinguish:

- Task created.
- Agent dispatched.
- Artifact generated.
- Pull request opened.
- Tests passed.
- Change approved.
- Code merged.
- Deployment completed.
- Production result verified.

Safe, policy-authorized low-risk changes may proceed through automated merge and deployment.

Changes affecting secrets, access privileges, payments, reward accounting or smart contracts require the applicable authorization and verification.

### Step 8 — User Revalidation

Notify the originating contributors when an improvement becomes testable.

Ask them to verify whether the change solved the original problem.

Accept additional feedback and reopen the work if needed.

### Step 9 — Impact & Reward Attribution

Associate the implemented improvement with its original contributors, builders, reviewers and testers.

Calculate eligible recognition and rewards without paying duplicate or fraudulent claims.

### Step 10 — Continuous Learning

Use verified product feedback and outcome data to improve future prioritization.

This learning must not silently modify foundational policies, permissions or economic rules.

# 27. AUTONOMOUS EXECUTION PROTOCOL

Begin by discovering the actual repository, available integrations, existing infrastructure and authorized credentials.

Reuse working components.

Do not introduce a new system when a compatible canonical service already exists.

Make and implement reasonable product decisions without unnecessary clarification.

Proceed iteratively:

**Inspect → Design → Implement → Test → Verify → Deploy → Observe → Improve**

Maintain a live task backlog, with explicit ownership and states.

When a task passes independent verification, feed the result into the next appropriate execution decision.

Keep Founder-level decisions separate from routine implementation.

Do not claim successful integration merely because an API contract was drafted.

Do not claim deployment merely because code was committed.

Do not claim token issuance merely because a contract was compiled.

Do not claim revenue, users, jobs, token holders, liquidity or paid contributors without observable evidence.

Where access to an external provider is missing, complete the rest of the production flow, identify the precise missing integration and maintain truthful feature status.
